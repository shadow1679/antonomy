## Architecture (from the design doc)

A public random seed drives a deterministic ant-colony simulation. Ants forage across a grid with 2 to 5 food sources, and each source stands for a preset option. The source with the most pheromone trail over the run wins: the trail near each source is summed every `SCORE_EVERY` (100) ticks and at the final tick. The ants add spectacle only. All entropy comes from the seed.

Pipeline: commit to a future drand round → close entries/stakes before it is published → seed = hash(drand randomness, request ID, contract address) → the contract runs the sim on-chain, a few ticks per permissionless call → after the final tick it computes winners and the decree hash and executes the capped action → anyone replays in the browser and compares the hash.

Core products, both built on one engine. **Positioning (decided 2026-10-26): forecasts are the headline feature and Memecoins With Mechanics is the main track.** The token's pitch is "Feed the swarm": $ANTO stakes steer each market's Community forecaster, and stakers get no payouts for being right. The main page shows forecasts first and Burn below. Details in `docs/FEATURES.md`.
- **Forecast colonies** (headline): for each Polymarket market, five colonies (Follower, Contrarian, Momentum, Community, Agents) run on their own maps. Three read a keeper-posted odds snapshot as food richness, Community reads $ANTO stakes, and Agents reads the forecaster agents' median odds. The average of their trail shares is the "swarm prediction"; a colony with no input (Community without stakes, Agents without posts) sits out of the average (decided 2026-10-27). There is no treasury effect and no payouts.
- **Burn colony** (core, second billing): picks the daily burn size from a fixed menu (0.10% to 2.00% of the treasury), hard-capped at 2% by the contract. Holder stakes steer it.
- **Recruit the swarm** (agents, decided 2026-10-27, on testnet since 2026-10-28; replaced Recruit an ant): anyone pays a $ANTO fee for a forecast on a Polymarket market of their choice. Agents are paid from the fee for work, never for being right: keepers post odds, forecaster agents post their own odds into a fifth colony (Agents), and crankers run the colonies. Agents use it through an `ask_swarm` / `post_forecast` / `verify` tool.

Everything in sections 9 and 14 (raffles, treasury mix, custom colonies, extra ant types) is optional.

## Constraints that shape any implementation

- **Determinism is the product.** The Rust (on-chain), JavaScript (live and replay pages) and Python (reference) implementations must produce identical result hashes across at least 10,000 seeds. Production code uses integer or fixed-point arithmetic only, with an integer PRNG, 16 or 32 discrete headings from a lookup table, no float, sin, cos or atan2, a fixed ant update order and a fixed tie-break (lowest index).
- **Gas bounds the design.** Use lazy evaporation (store the last-touched tick per cell and decay on read), so cost scales with ants and not with grid size. The per-transaction limit is 300 TGas. Ticks per call are unmeasured and must be measured on testnet first (day 2 of the build). Shrink ants, ticks or grid if a run doesn't fit.
- **Simulation parameters are immutable contract constants.** Prototype values: 72×48 grid, 150 ants, 800 ticks, 0.8% evaporation per tick, pheromone cap 20, score = pheromone within 6 cells of each source summed every 100 ticks and at the final tick, richness 0.35 to 1.3 for stakes and seeds, 0 to 1.3 in proportion for odds (decided 2026-10-27, so forecasts aren't flattened), flat stake base 2.5 sqrt-tokens per option (decided 2026-10-27 so stakes steer: 100 tANTO lifts an option from 20% to about 52% of Burn days; see `docs/FEATURES.md`). Forecast colonies may shrink to about 60 ants and 300 ticks. The Burn colony runs `BURN_TICKS` (43,200, from 12:00 to 24:00 UTC, the most any run may have); a trail fades to 0 after `FADE_TICKS` (852) ticks, which lets the sim clamp the decay table without changing any 800-tick result.
- **The colony chooses an index, never an amount.** Every action maps to a preset menu entry with a hard cap in the contract.
- **Seed → per-colony maps.** Each colony's map derives from the seed plus the colony's index. The seed also picks the map template and shuffles which option sits on which food source.
- **Fairness tests are required.** Each map template and each colony type needs at least 1,000 seeds. Every option must win close to its fair share, and none above about 30% for five options. The prototype's 100-seed test is only a smoke test.
- **Stakes.** One wallet budget across all colonies, square-root weighting, per-wallet caps. Staking closes before the drand round is published (for the Burn colony, at 12:00 UTC each day). The stake snapshot hash and the odds snapshot are both inputs to the sim, so the result is a pure function of seed, stakes and odds.
- **Forecast data trust.** Several keepers post independently and the contract takes the per-outcome median. Each snapshot stores a hash of the raw API response. The web pages read forecast inputs from the chain, never from outside APIs. The one exception is the Recruit page's search, which reads Polymarket only to pick a market to request (and, in the demo with no contract, stands in for the keepers).
- **Safety and liveness.** Advancing is permissionless with a small bounty. A deadline triggers the default action or a skipped round. A multisig behind a timelock can pause or override, and every use is logged.

## Product rules to preserve

- Forecasts are not betting. No payouts for being right, no links to betting venues, and every output is labelled as a forecast and not advice. Exclude markets about violence, deaths or private individuals.
- The hackathon reward pool uses a play token on testnet only. No mainnet deployment.
- The README must state the known limits plainly: seeds wait on drand being reachable (the contract checks drand's signature on-chain, so it trusts drand's network, not a keeper), and a Burn day is lost if nobody cranks it for about a day (the team's daemon does).
- Before submission, re-read https://nearhackathon.com/HACKATHON.md, since rules and dates may change. The repo must be public before 14 Nov 2026 23:59 UTC, with a README written for AI judges.
